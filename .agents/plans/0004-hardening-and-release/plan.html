Hardening, two missing operations, and a way to publish

gamelibrarymanager · main · 2026-08-17 · size: M

Eight phases. Each one closes alone, each one gives a version of its own, and no phase waits for a later phase. The order goes from the smallest cost to the largest, and the phase that publishes goes last by decision of the user.

Goal

The application stops in the three places where it can stop badly today: a request with no answer, two long operations at the same time, and a delete that compares against a list of thousands. It gains the two operations that a local-first application must have and does not have: to disconnect a store, and to take the data out. And the repository gains a way to publish what it builds.

Scope

In

  • A timeout on every request that the application makes.
  • A guard that permits one long operation at a time, and that clears itself when the command goes away.
  • The summary counts with COUNT, the delete of copies uses a temporary table, and the file database uses WAL.
  • A save writes one row and gives that row back. The interface stops asking for all of the library after each save.
  • A game that left every store says so, and a filter finds it.
  • To disconnect a store account, with the credential deleted.
  • To export the library, and a copy of the database before a migration.
  • A workflow that builds installers from a tag, and the visual check inside CI.

Out

  • An updater. It needs a signature key and an address that gives the manifest. That is a decision about distribution, not about this repository, and it does not belong in a phase that must close alone.
  • A wider connection pool. See the decisions: WAL gives faster writes, and more connections would give parallel reads, but Database::in_memory() gives a different empty database to each connection and all of the tests use it. The pool stays at one.
  • A data library in the interface. Phase 4 removes the refetch of all of the library after a save. It does not bring React Query, and it does not touch the load of the first start.
  • The plans 0001, 0002 and 0003. They record closed decisions. Nobody discusses them again.
  • Any change in crates/domain. No phase needs one.

Gap

Four kinds of change, and no phase needs a migration: every column that these phases use is already in the schema. The kinds are: a limit where today there is none (timeout, guard, temporary table); a count where today there is a list; a return value where today there is silence (the row that a save wrote, the state of a game with no copy); and two operations plus one workflow that do not exist at all.

Decisions

QuestionDecisionWhy, and what was refused
Where does the phase that publishes go?Last.The user decided it. The consequence is written down: the phases 1 to 7 close with a tag and with no installer. The workflow of phase 8 takes a tag as an input, thus you can run it against the earlier tags and get their installers later. Refused: to publish first, which was the recommendation because "each phase gives a release" is only true after phase 8.
What gives each closed phase?A minor version and a tag: 0.2.0 for phase 1, up to 0.9.0 for phase 8.The version goes in Cargo.toml, package.json and tauri.conf.json, which already agree at 0.1.0. Refused: one version at the end, which would make the eight phases one release and would disobey the request.
What happens when the user disconnects a store?A logical delete of the account and of its copies. The credential goes out of the store of secrets. game and user_state are not touched.It is the same rule as the switch by connector: the data that a store gave stays in the library with the status and the notes of the user. Refused: to delete the copies for real, which loses the history that lets a game come back; and to ask the user each time, which is one more decision for no gain.
What shape has the export?A complete JSON, a CSV with only what the user wrote, and a copy of the database before a migration.The JSON is the library; the CSV opens in a spreadsheet and carries the status, the score and the notes, which is the data that only this application has. Refused: only the export, which leaves the migration with no protection; and only the copy, which keeps the data inside the application.
How does the copy get made with a database that can be open?VACUUM INTO.One statement, and it is correct with WAL and with a live connection. Refused: fs::copy of library.db, which with WAL copies a file that misses the last writes, and which would make phase 7 depend on phase 3.
How much SQLite change?journal_mode=WAL, synchronous=NORMAL and busy_timeout, only on the file database. The pool stays at one connection.With one connection the commands still go one after another, thus this buys faster writes and not parallel reads. Parallel reads need more connections, and in_memory() gives a different empty database to each connection, thus every test would break. Refused: to widen the pool now, with no measurement that says the interface stops.
What happens to a game that left every store?It stays, with a mark, and a filter finds it. "Today" does not offer it.To hide it would hide the notes of the user with it, which is the only data that this application has and the store does not. The interface can find the state with no new SQL: the two lists of stores of LibraryRow are empty at the same time only in this case.
How does the user select where the export goes?tauri-plugin-dialog, with dialog:allow-save in the capability.A save dialog is what a user of a desktop expects, and the file goes where they want. Refused: to write in the data directory and to open the folder, which needs a permission as well and leaves the file in a place that nobody looks at.

Plan

Phase 1 — A request that gets no answer stops (0.2.0)

Today a store that accepts the connection and never answers holds the synchronisation for ever, and the cancel button does not reach it: cancelled() is examined between accounts, not inside a request.

FileChange
src-tauri/src/state.rsTake the builder out to pub fn http_client() -> reqwest::Client, with .timeout(30s) and .connect_timeout(10s). AppState::new calls it.
src-tauri/src/lib.rsExport http_client in pub mod testing, so that the test uses the same client as the application.
src-tauri/tests/offline.rsA test with a server that delays the answer more than the timeout. The connector gives a transport error and does not wait.

The login windows of GOG and of Epic wait on a channel and not on this client. The timeout does not touch them.

Done when: a provider that does not answer fails in less than 35 seconds, and a test proves it.

Phase 2 — One long operation at a time (0.3.0)

The three long commands — sync_now, refresh_prices and resolve_identities — share one cancel flag. Two at the same time cancel each other, and the first one to end clears the flag under the other. If the webview goes away and the command future is dropped, end_operation never runs.

FileChange
src-tauri/src/state.rsAdd operation: tokio::sync::Mutex<()>. try_begin() -> Option<OperationGuard> takes it with try_lock and clears the cancel flag. OperationGuard clears the flag in Drop. Delete begin_operation and end_operation.
src-tauri/src/error.rsAppError::Busy, with a message that a person reads.
src-tauri/src/commands/mod.rsThe three commands take the guard and give Busy when it is not free. The guard lives to the end of the command.
src-tauri/src/lib.rsExport what the test needs from state.
src/App.tsxThe message of Busy is shown as the other errors. The buttons keep the disabled that they have: this phase adds a guard, it does not move the rule to the interface.
src-tauri/tests/ (new)A second call while one runs gives Busy. A guard that is dropped leaves the flag clear.
docs/tauri/ (new)The convention: a long operation takes a guard, and the guard and not the command clears the flag.

Done when: two long commands at the same time give Busy and not a corrupt flag, and the flag is clear after the command goes away.

Phase 3 — The storage layer counts, and stops binding thousands of parameters (0.4.0)

Three changes with no effect that the user sees, and all of them inside crates/storage.

The delete must not be divided into batches of placeholders. NOT IN with half of the list deletes everything that is in the other half. The identifiers that the store gave go into a temporary table inside the same transaction, and the UPDATE compares against that table.

BEGIN;
CREATE TEMP TABLE seen (app_id TEXT PRIMARY KEY);
-- the identifiers go in, in batches of 500
UPDATE store_entry SET deleted_at = ?, updated_at = ?
 WHERE account_id = ? AND kind = ? AND deleted_at IS NULL
   AND store_app_id NOT IN (SELECT app_id FROM seen);
DROP TABLE seen;
COMMIT;
FileChange
crates/storage/src/repositories/store_entry.rssoft_delete_missing uses the temporary table. Add count_active(kind) -> i64.
crates/storage/src/repositories/game.rsAdd count_all() -> i64.
src-tauri/src/commands/mod.rslibrary_summary calls the three counts and unlinked_entry_count, which already exists. Take the body to a function that takes &Database, as sync, prices and identity already do, so that a test reaches it with no Tauri.
crates/storage/src/lib.rsopen adds journal_mode(Wal), synchronous(Normal) and busy_timeout(5s). in_memory is not touched.
crates/storage/tests/store_entry.rsAn account with 2,000 copies where 1,500 are still there: exactly 500 get the logical delete, and the 1,500 keep deleted_at IS NULL.
src-tauri/tests/summary.rs (new)The summary costs four statements. It counts with the same logger as one_query.rs, thus it must be alone in its file for the same reason that file gives.
docs/storage/ (new)The convention: a delete that compares against a list of the provider uses a temporary table, never a list of placeholders.

Done when: the summary makes four statements, a library of 2,000 copies deletes the correct 500, and a file database reports wal.

Phase 4 — A save writes one row, and gives that row back (0.5.0)

Today a status written on one game costs eight commands, all of the library, all of the review queue and all of the prices. A bulk save of thirty games costs thirty commands and then the same.

One constant, thus the row of a save cannot become different from the row of the list, and the plan test keeps its meaning.

src/features/game/GameDetail.tsx, src/features/library/BulkBar.tsx, src/features/today/Today.tsxThey use the row that comes back. The bulk bar makes one call and not one for each game.

Phase 6 — To disconnect a store (0.7.0)

The column deleted_at of store_account exists and nothing writes it. A user who changes their Steam key, or who wants GOG out, has no path.

FileChange

src-tauri/src/lib.rsRegister the command.

src-tauri/tests/ (new)After the disconnection: the account is not in active(), the secret is not in the store, a synchronisation does not ask that store, and user_state is the same.
docs/connectors/ (new)The convention: to disconnect deletes the credential and keeps what the store gave.

This phase does not need phase 5. Without it, the game stays in the library with no badges, which is what occurs today when a store loses a game.

Verification

Each phase closes with all of these green, which are the checks of AGENTS.md:

cargo fmt --all --check
cargo clippy --all-targets --workspace -- -D warnings
cargo test --workspace
bunx tsc --noEmit && bun run lint && bun test
bun run build && bun run visual
bun run tauri dev            # the window must open

And by hand, in the phase that changes it: phase 4, a save that does not make the list jump; phase 6, a disconnection with the notes still there after it; phase 7, the two files opened outside the application; phase 8, an installer downloaded and started.

Do not

  • Do not put two phases in one commit, and do not move work from a later phase to an earlier one. Each phase gives a version.
  • Do not divide soft_delete_missing into batches of placeholders. See phase 3.
  • Do not widen the connection pool, and do not touch Database::in_memory().
  • Do not write SQL outside crates/storage.
  • Do not give crates/domain a network or a database dependency. The architecture job of CI fails if you do.
  • Do not add an updater, and do not publish a release that is not a draft.
  • Do not declare a colour in a component: the tokens are the only source.
  • Do not touch the plans 0001, 0002 and 0003.
  • Do not write a new document in Spanish. The documentation is in English and obeys ASD-STE100.
