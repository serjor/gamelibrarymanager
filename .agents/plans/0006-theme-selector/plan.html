Decision context

What changes and why it matters

Behavior

Change: The user selects Light, Dark, or System in Utilities.

Why it matters: The user controls the visual mode without changing library data.

Mechanism: App owns the preference and gives it to UtilityPanel. Evidence: src/App.tsx:46-70 and src/App.tsx:326-364.

Visual system

Change: The stylesheet accepts an explicit active mode.

Why it matters: An explicit choice must override the operating system without a second palette in a component.

Mechanism: The root element receives data-theme="light" or data-theme="dark". The token blocks set color-scheme.

Code

Change: The shell gains one theme module and one labeled control.

Why it matters: The existing shell already owns maintenance controls. The feature does not need a new settings layer.

Mechanism: Add src/features/shell/theme.ts. Extend UtilityPanelProps in src/features/shell/UtilityPanel.tsx:16-33.

Data and contracts No change

SQLite tables, Rust commands, store credentials, library exports, and LibraryRow stay unchanged.

The preference uses one local WebView key. It is not library data and has no server consumer.

Accessibility

Change: Utilities gains a native select with a visible label.

Why it matters: The control keeps keyboard use, native focus, and screen-reader names.

Mechanism: Use a label tied to utility-theme. Keep the control available while a data operation runs.

Developer workflow

Change: Functional and visual tests cover explicit modes, storage, and System changes.

Why it matters: The current visual harness tests operating-system modes but not a user choice.

Mechanism: Extend test/visual/harness.ts:275-312 and test/visual/look.ts:716-830.

Boundaries

Approved scope

In

  • Three preferences: system, light, and dark.
  • system as the first-use preference.
  • Immediate application and persistence across application restarts.
  • One Appearance section inside the existing Utilities dialog.
  • System changes that update the active mode while the application stays open.
  • Theme application on the library, Utilities, setup, loading, and unlock surfaces.
  • Functional tests, visual tests, and an update to the existing color-token convention.

Out

  • A SQLite setting, migration, Rust command, or Tauri plugin.
  • Theme data in the database backup or JSON and CSV exports.
  • A selector on setup or unlock screens. The chosen theme still applies there.
  • Custom colors, custom themes, density choices, or account-specific themes.
  • Cloud sync, cross-device sync, and multi-window theme state.
  • New UI dependencies, a new settings framework, or a new palette.
  • Changes to storage, connectors, metadata, domain rules, or the library contract.
  • Edits to plans 0001 through 0005.
